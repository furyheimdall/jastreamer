# Agent guide

This is the entry point for agents helping with [jastreamer](https://github.com/furyheimdall/jastreamer). Read the relevant installation branch before proposing commands.

Reading this file is not permission to install software, stop playback, replace a service, publish a release, or change host security.

## 1. Route the request

1. Read [README.md](README.md) or [README.ko.md](README.ko.md) for the product and its supported targets.
2. Use [INSTALL.md](INSTALL.md) for English requests and [INSTALL.ko.md](INSTALL.ko.md) for Korean ones. The `INSTALL.md` links below use the same anchors in `INSTALL.ko.md`.
3. In the selected guide, follow the branch for the target platform and for a new installation versus an update. An existing deployment starts at [upgrade](INSTALL.md#upgrade), never at first-account setup.
4. Send everyday controls, settings, music browsing and troubleshooting questions to [INSTRUCTION.md](INSTRUCTION.md) or [INSTRUCTION.ko.md](INSTRUCTION.ko.md).
5. Inspect the authorized host and the repository revision matching the chosen artifact. Ask only for what that inspection cannot answer and for decisions affecting access, data or availability.

Do not make the user fill in a technical template or write configuration files. Explain the selected branch, then prepare the actual files after approval. Without host access, supply ready-to-save files and commands for the user's confirmed paths, inspect the results they return, and keep guidance clearly separate from work you actually performed.

## 2. Installation branches

| Request | Read first | Boundary |
| --- | --- | --- |
| Linux or Synology Server | [Linux Server](INSTALL.md#linux-server), `deploy/docker/server/compose.synology.yaml`, `packaging/server/server.json` | Linux `amd64` or `arm64`; DS918+ is `amd64`. The image includes Web Control, FFmpeg and the Linux AirPlay runtime. |
| Native Windows Server | [Windows Server](INSTALL.md#windows-server) | Portable Windows x64 ZIP: embedded Web Control, UPnP/DLNA and opt-in Cast, without bundled AirPlay or FFmpeg. |
| Desktop Control | [Windows ZIP](INSTALL.md#desktop-windows) or [Linux DEB](INSTALL.md#desktop-linux) | Client of an existing Server, browser audio by default. Compatible Windows builds add opt-in WASAPI shared/exclusive output and Server-owned SMTC; Linux keeps browser audio. No independent saved-music player and no ARM64 Desktop package. |
| Native Android client | [Android](INSTALL.md#android) | Kotlin/WebView, Server-controlled Media3 output and independent Saved music; Android 10+ with isolated Server profiles. New imports need compatible v1 Server/Web downloads; completed music needs no account or Server. Install the signed release APK attached to the selected release; CI APKs stay development-only. |
| Native iOS development | [iOS source and CI](INSTALL.md#ios) | SwiftUI/WKWebView, iOS/iPadOS 18.4+. Source, simulator tests and unsigned device builds only; no installable phone package and no Apple distribution. |
| Phone browser or PWA | [PWA](INSTALL.md#pwa) | Server-hosted UI. PWA installation needs a trusted HTTPS origin, except local development. It is not an offline player; native mobile clients are separate branches. |
| Upgrade or recovery | [Upgrade](INSTALL.md#upgrade), [rollback](INSTALL.md#rollback) | Preserve the current deployment and its state; never treat an upgrade as a clean installation. |

## 3. Inspect and agree before changing the host

**Host and access.** Establish the authorized connection method, the target user's actual home directory, OS and architecture, available container tooling and whether it works without sudo (or the native Windows target), LAN routing, listener ports and conflicts, and whether a Server is already running or playing. Never assume sudo is available.

**Paths.** For a new ordinary Linux installation, default the saved project to the target user's `~/.config/jstreamer`, with separate `config` and `data` children. Resolve `~` on the target host, not on the agent workstation, and do not default to `/srv/jastreamer` or `/data/music`. Synology uses its approved persistent project/share paths. Existing deployments keep their paths unless a migration is separately approved. Keep project, config and data outside the music root and reject overlaps that could expose application state.

**Music root.** A music-path decision is mandatory before Linux/Synology setup proceeds.

- Ask for the user's existing absolute host music root. A blank answer or “Skip” is not permission to choose or create a directory.
- If the user has no music folder, ask explicitly: “May I create and use `<your-home>/music` as your music folder?” Show the resolved absolute path and create it only after consent.
- If that path already exists, inspect it and confirm reuse without replacing it. Never create a missing user-supplied root to hide a typo.
- Create or reuse only the approved root's `jastreamer-samples` child for bundled samples, and mount the approved root read-only at `/music`.
- Native Windows keeps its separately documented existing-root or explicit package-adjacent sample-only choice.
- Tell the user the exact host music path and that an empty folder has no playable tracks: they must put music there and run **Settings → Library → Scan now**. Identify copied samples as test tracks rather than the user's music, and explain that personal music goes into the same approved root and must be scanned. Report what was actually found; never describe an empty library as playback-ready.

**Permissions.** A home-directory location does not by itself grant container access. Verify that runtime UID/GID `10001:10001` (with the actual Docker UID mapping) can write config/data and read/traverse music. If access is missing, obtain approval for a narrowly scoped permission/ACL change or report the missing prerequisite. Never use sudo implicitly, change the whole home or music tree, or silently change the container user.

**Release selection.** Select the newest compatible, published, non-draft **Server** release from the complete [Releases listing](https://github.com/furyheimdall/jastreamer/releases), comparing publication times. Prefer a stable release (`vX.Y.Z`); choose a preview (`vX.Y.Z-preview.N`) only when the user explicitly wants one, or when it is newer than every stable release and compatible with the deployment. Do not rely on `/releases/latest` alone: it returns only the newest stable release and omits prereleases, so read the full listing before deciding. Read the selected release's limitations and verify its provenance, source revision, manifest, SHA-256 values, architecture and immutable GHCR digest. A public GHCR image needs no registry password. Do not invent an artifact, use a mutable `latest` tag, silently substitute a build, remove a preview label, or claim that unreleased repository features exist in an older release.

**Android artifacts.** For an Android installation or update, use the signed release APK attached to the selected release. Verify its published SHA-256 and check the signer with `apksigner verify --print-certs`, comparing the digest case-insensitively against the fingerprint pinned in `packaging/android/release-certificate-sha256.txt` and repeated in the release notes; stop and report any mismatch instead of installing. APKs from CI runs remain development and testing artifacts, and a pull-request artifact is never a release. Never request, hold, transfer or use Android signing keys, keystores or their passwords, and never sign an artifact yourself: signing happens only in the maintainer-approved release workflow.

**Proposal and approval.** Propose the exact mounts, saved configuration, client LAN URL, permissions, network access, image/package replacement and interruption in one place, covering Server name, music choice, HTTP/HTTPS, selected network interfaces and access restrictions, the Server URL used by playback devices to fetch audio, transcoding, optional outputs and UI language. Explain every non-default setting. Keep Google Cast disabled unless it is explicitly selected; Cast needs no Chrome or Python helper. Obtain approval for the deployment change, and separate approval for installing host tooling, narrowly changing permissions or firewall rules, stopping playback or a service, and pairing or controlling a receiver. Approval given for another PR, release or deployment does not carry over.

**Credentials.** Never request or record passwords, private keys, registry tokens, session cookies or other credentials in chat, Git, generated instructions or logs. Use existing secure credential handling or private interactive entry. For HTTPS, ask for certificate and key **paths**, not key contents. Do not bypass certificate validation or expose the NAS publicly to make PWA installation work.

**Materialize the result.** For a new agent-assisted installation, leave a working deployment rather than a recipe: save the repository Compose definition in the project, write its persistent environment file with resolved paths and the pinned image digest, and prepare the actual `server.json`. Seed samples only from a verified release that contains the documented sample manifest and payload. On Linux/Synology, run that image's `/usr/share/jastreamer/seed-samples.py` against the approved `jastreamer-samples` host directory before mounting the parent read-only at `/music`; the seeder may retain byte-identical files but must not replace a conflicting file, must preserve the source root's owner and permissions, and must never recurse over it. With a verified Windows package containing the documented samples, a first launch with no `server.json` seeds its adjacent `music/jastreamer-samples` and never overwrites existing config or music; prepare an approved alternate root explicitly before launch.

## 4. Install or upgrade without losing state

Follow the selected INSTALL branch instead of duplicating its commands here.

- **Reuse the existing deployment.** Keep the existing Compose project name, directory, files, environment and mounts. Save actual deployment inputs persistently; never depend on temporary shell exports or leave unresolved placeholders. Keep the complete architecture-matched Linux image instead of replacing it with a bare Go binary or installing its media dependencies on the host.
- **Reconcile before you change anything.** Compare the running deployment with its saved inputs: actual container `Mounts` and config argument/environment, the rendered existing Compose/environment, and the current config's `data_dir` and every library root. Record each config/data/music path's host source or named volume, container destination, resolved symlink target, ownership, permissions and read/write mode. On native Windows, inspect the actual launcher/config and resolve data and music paths, including external drives and UNC shares. Stop on disagreement, missing mounts or unreadable paths; never substitute new-install defaults.
- **Preserve the security posture.** Keep UID/GID `10001:10001`, the read-only container root and music, writable config/data only, dropped capabilities, `no-new-privileges`, temporary storage, host networking and the documented restart policy. Keep container `data_dir`, library roots and packaged helper paths consistent with their mounts. Additional music roots need separate approved read-only mounts.
- **Never weaken the host.** No privileged mode, Docker socket mounts, disabled firewall or sandbox, `chmod 777`, or recursive ownership/permission changes on music. Do not add bridge port mappings to the host-network deployment. Keep Chromium's packaged setuid sandbox for the Linux Desktop DEB.
- **Preserve state.** Keep accounts, sessions, Server UUID, settings, library, likes, artwork, queue order and position, playlists and device credentials. Do not overwrite existing config/data, remove volumes or reset accounts. Let the user create the first account privately; an existing account requires login, not setup. Samples are optional during an upgrade: add them only after explicit approval, from the verified release payload, without replacing existing music or state and without scanning, queuing or playing automatically.
- **Replace only what the package owns.** Download and verify the target before any downtime and retain the old image/package identity. An update replaces only the image or package-owned files and reuses the existing config/data/music paths and Desktop profile in place. Do not perform or require backups, snapshots or restore verification as part of an update. Check the release's configuration and database compatibility before replacing the service; a storage migration is a separate, explicitly approved operation. On Windows, preserve the existing `server.json`, `data` and `music`, and preserve Desktop `user-data` separately.
- **Validate before starting.** Check the prepared Compose configuration and run the target Server's `--check-config` with its actual mounts.
- **On failure, stop cleanly.** Retain diagnostics and use only the approved rollback plan. Confirm that the previous image/package supports the current configuration and database before downgrading; if compatibility is unknown, stop and report it without resetting or rewriting data. Never repeatedly replace a failing service or weaken checks to claim success.

**AirPlay sending** is supported only by the Linux `amd64`/`arm64` container, whose verified package supplies Python 3.12, pinned pyatv 0.18.0, FFmpeg and `/usr/local/bin/jastreamer-airplay`. An external helper path is not arbitrary Python, `atvremote`, or receiver software such as Shairport Sync: it must implement jastreamer's adapter protocol with compatible dependencies, using the adapter source and dependency file from the **same release as the installed Server**, not an arbitrary `main` revision. The [adapter source](https://github.com/furyheimdall/jastreamer/blob/main/apps/server/internal/airplay/helper.py), [locked requirements](https://github.com/furyheimdall/jastreamer/blob/main/packaging/server/requirements-airplay.txt) and [pyatv 0.18.0 source](https://github.com/postlund/pyatv/tree/v0.18.0) links are references, not a guarantee that `main` matches an installed release. The Desktop may block external windows, so its help popup prints copyable full URLs. Native Windows Server does not support AirPlay, regardless of the path entered in Settings.

## 5. Verify and hand over

1. Verify the running image/package identity, health and logs, mounts and security settings, and persistent state. Check the Web UI through the real client LAN route, not only `localhost`.
2. After a private login, apply the agreed language and settings, scan the actual music roots and inspect the completed result. Confirm output discovery without silently selecting, pairing or playing a receiver. Without browser access, guide these steps and check the user's result.
3. Keep playback Server-owned:
   - One queue and one selected output; explicit resume after a terminal reconnect or process restart.
   - No Stop to network outputs when Control closes or changes its Server selection. A page that owns browser output releases that local transport on closure or reload.
   - A newly opened page may atomically replace an offline selected output with this device only while stopped or unavailable and without active commands: preserve queue and position, reject concurrent state changes, and never autoplay or take over Android Saved music or another Server's ownership.
   - Terminal loss on the same page must not continually re-register. Android native output survives Activity/WebView recreation while its service and registration remain valid. Windows Desktop **X** hides the resident window; tray **Exit** releases the local transport.
   - UI navigation, PWA installation and player-panel expansion must not send playback commands.
4. Distinguish a healthy Server, media retrieval, receiver-observed playback and actual audible output. CI, signatures, browser emulation and a discovered receiver do not prove physical audio qualification. Preserve real errors and unsupported-operation boundaries.
5. Report the verified clickable LAN URL, exact version/digest/hash, preserved paths and mounts, checks performed and remaining prerequisites, without secrets. Invite the user to select their intended output while stopped, play a track, confirm sound, try supported pause/seek, then Stop. These are user-run checks, not authorization for automatic playback.

## 6. When the request is a code change

**Layout.** The Go Server is in `apps/server`, the shared React Web Control in `apps/control`, the Electron Desktop wrapper in `apps/desktop`, and the native Kotlin/WebView client in `apps/android`. Use the actual targets in [Makefile](Makefile), the component manifests and the Android Gradle Wrapper. Verify the affected component and its actual UI/API behavior; a successful build of one component does not qualify the others. Installation assistance is not permission to commit, push, merge, release or deploy unrelated changes. Keep installation procedures in INSTALL and detailed UI behavior in INSTRUCTION rather than growing the README again.

**Android.** Unit, lint and APK checks plus real-emulator Web UI tests run in `.github/workflows/android.yml`; reuse its x86_64/KVM execution path with isolated fixtures, never a user's Server or playback state. Android uses one Media3 engine with an explicit Server/Local ownership handoff: Server mode keeps Server-owned commands, while Saved music owns an independent, duplicate-preserving local queue. Verified completed imports stay usable without accounts or Server access; pending transfers stay origin- and principal-bound. Restrict native output and download bridges to the verified current main-frame document, keep credentials native, and isolate profiles by Server UUID and origin including port. No generic native bridge, no automatic synchronization of completed music, and no autoplay after a restart or terminal loss. Registration on new-page entry is limited to the guarded fallback above and must not supersede an explicit playback request. Local volume changes only the owning audio engine, never the system or another output.

**Android USB bit-perfect** is an opt-in, default-off app preference (`native_audio_settings`) for Server-owned playback only; Saved music keeps the standard Android output. Requesting it needs API 34 `AudioManager` preferred mixer attributes with `MIXER_BEHAVIOR_BIT_PERFECT` on a `TYPE_USB_DEVICE`/`TYPE_USB_HEADSET` output whose `AudioFormat` exactly matches the stream Media3 will open; never substitute a near format or the mixed output, and fail the track instead. Change it only while phone playback is stopped, apply it from the next track, keep the same output registration, and fix the app volume at 100% while it is on. Report the actual path from the initialized `AudioTrack` and the framework's preferred mixer attributes, keep the decision rules in `UsbBitPerfectPolicy` unit tested, and clear the preference when the setting is turned off, the device detaches, Server ownership ends or the service stops. Media3's `DefaultAudioSink` writes 16-bit PCM here, so never claim bit transparency for a source whose precision was reduced.

**Windows native audio** lives in `apps/desktop/native/audio`. Build it with the pinned dependency downloader and `npm run build:native:win` from the x64 MSVC developer environment with Windows SDK, CMake, Ninja and MSYS2 (make/nasm); `npm run package:win` includes the helper, the shared LGPL FFmpeg libraries, licenses and corresponding sources. Native preferences stay in portable `user-data`. Never silently substitute shared mode for requested exclusive mode, infer bit-transparent delivery from the toggle alone, expose session credentials or media URLs to the helper, or let SMTC mutate a local queue. The Browser backend has no endpoint or Exclusive selection, and Exclusive mode fixes the application volume at 100%. A same-Server WebView reload retains live native ownership; active native playback must stop before backend, endpoint, mode or Server changes, and Quit releases local ownership only. When the Server releases the registration — for example after a Server restart — report a lost playback connection, not a sign-in failure; a rejected credential or an untrusted certificate remains its own error. Preserve failed or absent Windows build, physical endpoint, audible-output and DAC evidence as unverified; portable decoder, packing and protocol tests do not qualify WASAPI or SMTC on hardware.

**iOS.** Native SwiftUI/WKWebView source is in `apps/ios`, using the shared `Jastreamer` Xcode scheme. `.github/workflows/ios.yml` pins Xcode 16.4 and iOS 18.5, runs unit and actual-Web-UI simulator scenarios, and builds unsigned device bundles. The minimum iOS/iPadOS version is 18.4 so that native file-picker denial uses a public API. Keep profiles isolated by verified Server UUID and canonical origin including port. Do not add a native JavaScript bridge, shared-store fallback, standalone native audio engine or native lifecycle playback commands. The client is controller-only and its WebView blocks media loads, so never present a Local playback entry or claim the browser-output path works inside it. This source/CI scope does not authorize Apple credentials, signing, device installation, TestFlight/App Store publication or deployment, and simulator results are not physical-device, Wi-Fi/Bonjour or audible-playback qualification.
